Eko Architecture

How a teeka draft moves through Eko: verified Gurmukhi in, layered checks that cite their evidence, human decisions with reasons, and a rule loop that can't quietly drift from SikhRI's approved work.

PerformanceSpeed wins over data locality: hosted models are fine. Code checks return in under a second; LLM checks run in parallel per tukk.
NoisePrecision over recall: a check that can't verify its finding reports a hint, not a flag.
CostLLM calls run only after a prefilter selects the line, and every response is cached by its inputs.

Logical architecture

Five zones. Gurmukhi is analyzed by deterministic code; the LLM only judges English against structured evidence. Numbered markers match the notes below the figure.

Deterministic code Calls an LLM Human decision Data Rule-change loop
  1. 1

    BaniDB + normalizer

    Gurmukhi and its metadata come only from a local copy of the BaniDB database, read by the ingest script and normalized to Unicode NFC once. BaniDB's attribution and logo go in the app footer. Every line and word gets a stable ID. Nothing downstream types, edits or generates Gurmukhi.

  2. 2

    Morphology analyzer

    Splits each word into stem and ending matra and emits candidate grammatical features. The matra is kept as a feature, never stripped. For now the stem key powers TERM-02's Divine-name matching. Grammar hints are P1: a free transcreation doesn't map word for word onto the line, and without a dictionary many endings stay ambiguous.

  3. 3

    Rule compiler

    The free-text rule stays the source of truth. An LLM compiles it into a check plan: glossary match, prefilter + LLM confirm, grammar-conditioned, or pure style. The plan is shown beside the rule so reviewers can see how it will be enforced.

  4. 4

    Layered engine, cheapest first

    L1 runs deterministic glossary and regex checks. L2 calls the LLM only for lines a prefilter or plan selects. Gurmukhi matching finds Divine names by stem for TERM-02. L3 retrieves approved precedents: lexical on the Gurmukhi side, embeddings on the English side.

  5. 5

    Citation validator

    Drops any flag whose quoted span isn't literally in the draft, or whose rule or precedent IDs don't exist. This is what makes "every flag explained and cited" enforceable rather than hoped for.

  6. 6

    Reviewer decisions

    Accept, override and waive each require a short reason, stored with the reviewer's name and shown to every later reviewer. Any edit sends the draft back through the engine.

  7. 7

    Drift check

    Anyone can propose a rule in free text; proposals drafted from repeated overrides are P1. Contradictions, glossary collisions, and rules that would flag already-published work are blocked. Anyone can override a block, and the reason is stored with the rule.

  8. 8

    Backtest harness

    Replays held-back pre-edit drafts through the same engine and compares its flags with the corrections reviewers actually made. Typos and other non-rule corrections are tagged separately so they don't distort the catch rate.

Lifecycle of one shabad

The same system, read as a sequence of who acts when. Kesri tags mark the six beats the submission video has to show.

  1. a

    Edit loop

    Every save re-runs the engine on the changed tukks only. The report card always reflects the current text, so a reviewer never approves against stale flags.

  2. b

    Approved set grows

    Final approval publishes the translation into the approved set and re-indexes it for style retrieval. Lines approved with a waived flag carry that mark, so a one-off exception isn't learned as the norm.

  3. c

    Evaluation stays offline

    The evaluation lane reads held-back history and never writes to live drafts, decisions or rules. Scores are stored per ruleset version so the demo can show the effect of a new rule.

Technical architecture

Built in one full day by two people, each working with an AI coding agent: TypeScript end to end, one Next.js process, one SQLite file, and a provider-agnostic LLM layer so the fastest good model can be picked after the bake-off.

What happens on save

POST /api/check        // code checks, returns at once
  diff draft → changed tukks
  L1 rules (TERM-01/03/07,
     LAYER-06/07) → findings
  save → report card shows them

POST /api/check/llm    // UI calls right after
  prefilters pick (line, rule) pairs
  build packet per pair
  cache hit? use it : adapter call
  validator drops bad spans / IDs
  save → report card updates

Two calls instead of streaming keeps the build simple: reviewers see code findings instantly, and model findings arrive a few seconds later.

How two people and their agents work without collisions

Merge conflicts come from two agents editing the same files, not from git itself. Three ways to set this up:

OptionHow it worksProsCons
A. Split by folder (recommended)Each person and their agent owns a set of folders. Shared contracts are written together in hour 0–1 and then frozen. Small commits to main, pull and rebase every hourBoth people build at full speed; conflicts are rare because nobody edits the other's filesNeeds an hour of setup discipline; a contract change needs a quick heads-up
B. One driver, one set of agentsOne person runs the coding agents (several in parallel, each in its own git worktree). The other handles the SikhRI sample, the reviewer document, test data, QA and the videoNo merge conflicts at all; the non-coding work is real and neededCoding throughput is one person's attention; the second engineer barely codes
C. Pair on one machineBoth people steer one agent session togetherZero conflicts, shared understandingRoughly half the output; fine for the last two hours, wasteful all day

Recommendation: A for hours 1–9, then C for the last hour of integration and recording.

Ruleset v0.1

66 rules drawn from SikhRI's published Approach and Methodology pages, each with its strength level and source. Eko checks the English transcreation only, so rules for the literal translation, annotation and transcription wait. Rule text stays verbatim; the team's judgment calls sit beside each rule in rules.resolved.json, and the open ones go to the reviewer in a separate document.

8 checks on the transcreation 1 met by design 1 suppresses false flags 32 later (literal, annotation, transcription) 11 reviewer guidance 9 process only 3 removed by the team 1 merged

Severity follows the draft's strength levels

Error

MUST rule checked by code with near-zero false positives. Blocks publishing until fixed or waived with a reason.

Flag

MUST rule confirmed by the LLM against the BaniDB line. Blocks publishing until fixed or overridden with a reason.

Warning

SHOULD rule. Needs a reason to dismiss; never blocks.

By design

Eko's workflow makes the rule impossible to break, or the rule only switches other warnings off.

What crosses the LLM boundary

The LLM gets a structured packet, not raw Gurmukhi to interpret. Its answer is a JSON flag that the validator checks before anyone sees it. Values below are illustrative.

Evidence packet → LLM

// built by code, per line × rule
{
  "line_id": "L-000123",
  "gurmukhi": "<from BaniDB>",
  "divine_terms": [{
    "surface": "ਕਰਤਾ",
    "attribute": "Creator"
  }],
  "english_draft": "The Lord sustains all creation.",
  "layer": "transcreation",
  "rule": {
    "id": "TERM-02",
    "level": "MUST",
    "text": "Retain the specific Divine attribute
             the original Sabad uses …",
    "plan": "grammar_conditioned"
  },
  "precedents": [{ "id": "T-0456", "english": "…" }]

TERM-02 needs the Gurmukhi from BaniDB, which is why it's an LLM check. Pronouns for the Divine are still an open question in the ruleset, so there's no pronoun rule yet.

Drift check

Runs on every proposed rule before anyone approves it. Anyone can override a block, with a reason that stays on the rule's record.

CheckHowOutcome
ContradictionRetrieve related rules; LLM labels each pair contradicts / overlaps / unrelated, with a reasonBlock
Retroactive impactReplay the proposed rule over every approved translation and count the lines it would flagBlock above threshold, affected lines listed
Glossary collisionCompare new renderings with existing preferred renderingsBlock
DuplicateSimilarity against existing rulesWarn suggest merge
Scope changeLLM compares with the rule it narrows or broadensWarn show both

Retroactive impact is the strongest signal: it measures drift against SikhRI's actual approved work rather than a model's opinion, and it demos well ("this rule would have flagged 7 approved lines").
